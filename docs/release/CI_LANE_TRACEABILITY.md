# Claim2Car CI Lane Traceability

**Purpose:** state exactly what each automated lane proves, what it does not prove, and which execution slice it protects. A passing workflow is evidence for its assertions only; it is not a general release certificate.

**Candidate topology at the audit baseline (2026-11-10):** PR #29 is the broad implementation candidate (224 commits ahead of `main`, 93 changed files). PR #31 is a stacked Slice 2 workbench increment (20 commits, 13 changed files at the audit baseline) whose base is PR #29's implementation branch. The current branch head and run links must be recorded from GitHub for every release decision; do not reuse historical SHA/run IDs as current evidence.

## Hidden assumptions and integration gaps

1. **Path filters are asymmetric unless reviewed.** The integrated-container workflow's `push` filter included `frontend/**`, while its `pull_request` filter did not. A frontend-only PR could therefore omit the integrated image/route smoke. The audit follow-up adds `frontend/**` to the PR filter. Keep both trigger path sets aligned and test the workflow definition when changing them.
2. **A green aggregate can hide a skipped deploy.** `railway-deploy.yml` verifies the restricted service; its deploy step/job may be skipped. The integrated staging workflow is a different manual-only workflow with different prerequisites. Always inspect job and step conclusions, not just the run's green conclusion.
3. **The database lanes cover different schema phases.** The full suite and legacy component lane intentionally use a shared pre-cutover baseline through 0007; the authority lane migrates the primary diagnostic database through 0017 and runs isolated full-plan exercises. These results are complementary, not interchangeable. The release evidence pack must explicitly identify which tests ran against which schema phase. Do not imply the entire full suite ran against the post-cutover authority schema unless a run proves it.
4. **Browser tests have different fidelity.** Node controller assertions, Chromium IndexedDB tests with a mocked uploader, and integrated-container HTTP route tests cover separate seams. None alone proves a real-device capture followed by durable API/database/object-store persistence.
5. **Synthetic evidence is not field evidence.** Controlled demo, fake credentials, synthetic tenant IDs, mocked uploads, and disposable volumes validate controlled behavior only.
6. **Diagnostic success is not acceptance.** The database authority workflow's own structured report awards zero gates and reports acceptance not run. Formal gate results require the separately governed acceptance process and an accountable decision.
7. **A PR stack is not a merge-ready slice by default.** PR #31 targets PR #29's implementation branch, not `main`. It is reviewable as an increment against that base, but it cannot be treated as an independent mainline merge without first integrating/rebasing its prerequisite changes.

## Required release-evidence record

For each candidate SHA, record: workflow name; run ID/URL; tested SHA; conclusion; job/step-level skipped status; environment/schema phase; artifact URL; requirement/slice protected; limitations; and reviewer/acceptance decision. A check from another SHA, branch, or schema phase cannot satisfy the current candidate's gate.
